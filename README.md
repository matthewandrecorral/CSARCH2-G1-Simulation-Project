# Fully Associative Cache Policy Lab

A browser-based CSARCH2 simulator that runs Least Recently Used (LRU) and Most Recently Used (MRU) fully associative caches side by side. Both policies start empty, receive the same validated block-address sequence, and expose every hit, miss, load, eviction, recency update, latency, and aggregate statistic.

## Features

- Configurable power-of-two block size and cache-line count.
- Fixed 1,024-block main memory with validated addresses from 0 to 1,023.
- Required sequential, mid-repeat/reverse, and 64-access random generators, plus custom input.
- Repeatable random sequences using an optional seed.
- Step forward/back, seek, play, pause, reset, speed selection, and final-snapshot mode.
- Side-by-side LRU/MRU cache states, replacement explanations, and synchronized text trace.
- Load-through and non-load-through timing with editable cache and block-fetch latency.
- Hits, misses, rates, total time, and Average Memory Access Time (AMAT) for both policies.
- Responsive layouts and reduced-motion support.

## Using the simulator

1. Choose the block size and number of cache lines. Both must be powers of two; the minima are 2 words and 4 lines.
2. Select load-through or non-load-through and enter positive timing values in nanoseconds.
3. Choose a required sequence or enter custom comma/whitespace-separated block addresses.
4. Select **Run LRU / MRU comparison**.
5. Inspect the full statistics, then use the playback controls and trace to explain where the policies diverge.

Changing a configuration, sequence, or timing value clears the previous result so stale values are never shown with new inputs.

## Cache and timing model

Inputs are block addresses, not word addresses. Block size describes the transferred block but does not change the hit/miss pattern. On a miss, the lowest empty slot is filled first. Once full, LRU evicts the least recently accessed block while MRU evicts the most recently accessed block. Hits and loads both update recency.

The timing symbols are:

- `C`: cache lookup/access time.
- `M`: time to fetch one complete block from main memory.
- Hit latency: `C` for either read policy.
- Load-through miss: `C + M` because the requested word is forwarded during the fill.
- Non-load-through miss: `M + 2C` because the filled block is read from cache again.
- Total time: `(hits × hit latency) + (misses × miss latency)`.
- AMAT: `total time / accesses`.

The editable defaults, `C = 1 ns` and `M = 100 ns`, are teaching values rather than measurements of real hardware. Both read policies allocate a missed block; the policy changes latency only.

## Reproducible required-sequence results

The following results are generated by the implementation using 4-word blocks, 4 cache lines, load-through, `C = 1 ns`, and `M = 100 ns`. The random case uses seed `group-1`. A dedicated automated test locks these values to the code.

| Sequence | Policy | Accesses | Hits | Misses | Hit rate | Total time | AMAT |
|---|---:|---:|---:|---:|---:|---:|---:|
| Sequential | LRU | 16 | 0 | 16 | 0% | 1,616 ns | 101 ns |
| Sequential | MRU | 16 | 4 | 12 | 25% | 1,216 ns | 76 ns |
| Mid-repeat/reverse | LRU | 40 | 4 | 36 | 10% | 3,640 ns | 91 ns |
| Mid-repeat/reverse | MRU | 40 | 17 | 23 | 42.5% | 2,340 ns | 58.5 ns |
| Random (`group-1`) | LRU | 64 | 0 | 64 | 0% | 6,464 ns | 101 ns |
| Random (`group-1`) | MRU | 64 | 1 | 63 | 1.5625% | 6,364 ns | 99.4375 ns |

For these particular patterns, MRU retains older blocks that are revisited later and therefore outperforms LRU. This is workload-specific, not a general claim that MRU is superior. The seeded random sequence has almost no locality with only four cache lines, so both policies are dominated by misses.

## Assumptions and limits

- All operations are reads; writes, dirty bits, and write policies are out of scope.
- The assignment does not define read-policy latency precisely. The formulas above are the project’s documented interpretation and should be changed if the instructor supplies a course-specific formula.
- `M` is modeled as a complete-block fetch because inputs contain no word offsets.
- Seeded generation hashes the trimmed seed with 32-bit FNV-1a and uses Mulberry32. Blank seeds use `Math.random`.
- The required `0..2n-1` patterns are available through `n = 512`; beyond that, their addresses exceed main memory. Larger valid caches can use custom/random sequences.
- The UI limits visual runs to 4,096 cache lines and 250,000 recorded line snapshots per policy to protect browser resources. The browser-independent engine has no assignment-defined cache maximum.
